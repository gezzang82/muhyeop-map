## 1. 데이터 흐름

```
[수집] 플랫폼에서 신규 캠페인 긁기
   ↓
scraped_items (승인 대기 큐)
   ↓
[AI 검증 = 오토파일럿] 3갈래 자동 분류
   ├─ 🟢 자동등록 → 매장·캠페인 생성 → 즉시 지도 공개
   ├─ 🟡 검수 대기 → 운영자가 어드민에서 확인 (애매한 것만)
   └─ 🔴 스킵 → 버림 (마감 지남 등)
```

- **검증 시점**: 수집 직후 자동. 별도 트리거 없음.
- **공개 시점**: 자동등록되는 **즉시** 지도(muhyeop.com)에 반영. "올리기" 버튼 없음.

## 2. 실행 경로 — 로컬 크롤러 단일 (Vercel 크론 폐지 2026-08-30)

**로컬 크롤러(`scripts/crawl-worker.js`)로 단일화.** 과거 매일 06:00 KST Vercel 크론은 **폐지** — ①디너의여왕만 커버 ②컴퓨터 켜진 06:00엔 로컬 크롤러와 오토파일럿이 겹쳐 **같은 매장 2중 등록(중복매장)** 위험이 있었다([[06-decision-log]] 2026-08-30).

| 실행 | `scripts/크롤러-시작.command` 더블클릭(또는 재실행) |
|---|---|
| 플랫폼 | 디너의여왕·강남맛집·링블·포블로그·서울오빠·리뷰노트 |
| 지역 | 전국(디너의여왕 지역순회 + 나머지 전국 피드) |
| 컴퓨터 | 켜둔 동안만 (끄면 수집 정지) |
| 처리량 | 무제한(켜둔 만큼, 따라잡으면 10분 유휴 대기) |
| 검증 | 플랫폼별 수집 직후 즉시 오토파일럿 |
| 멈춤 | 창에서 Control+C |

- **평소**: 저녁에 컴퓨터 켤 때 크롤러 더블클릭 → 그날 신규분 수집·자동등록. 체험단 마감이 ~5일이라 하루이틀 걸러도 지장 없음.
- **⚠️ 동시 실행 금지**: 크롤러를 두 개 띄우면 오토파일럿이 겹쳐 중복매장이 생긴다(2026-08-30 실제 발생·병합 정리). 항상 **1개만**.
- **코드 갱신 후엔 재시작**: `_scrape.js`/`_autopilot.js`를 수정·배포하면 돌던 크롤러는 옛 코드라, 새 로직을 적용하려면 크롤러를 재시작한다.

## 3. 운영자가 하는 일 (거의 없음)

1. **평소**: 아무것도 안 해도 됨.
2. **빨리 채우고 싶을 때**: `크롤러-시작.command` 더블클릭 (끌 땐 Control+C).
3. **검수**: 어드민 → 매장/캠페인 등록 → 데이터 수집 → **승인 대기**의 🟡 소수만. 각 행 `검수` 열의 사유(`auto_note`) 보고 [승인]/[수정]/[반려].
4. **AI 등록분 확인/회수**: 어드민 조회 → 캠페인 → 출처 **AI** 필터. 문제 있으면 해당 행에서 숨김/삭제.

## 4. AI가 자동으로 판정하는 기준

- **기본 승인** — 플랫폼에서 온 정상 데이터라 전제. 협찬 내용이 짧거나 홍보성인 건 정상(반려 안 함).
- **반려(검수로)는 명확한 문제만**: 스팸/의미없는 매장명, 배송형/무매장, **같은 위치(300m)의 진짜 중복**.
- **카테고리 교정**, 요일·카테고리 불확실은 자동등록 막지 않음(요일은 비워서 등록).
- **오등록 방지 페일세이프**: AI 호출 실패·저신뢰면 자동등록 안 하고 검수큐로.

## 5. 안전장치 (중복·오등록 방지)

- **중복 매장 방지**: 같은 이름+좌표면 매장 재사용(채널별 캠페인만 추가). 승인은 순차 실행(동시 등록 경합 차단).
- **중복 캠페인 방지**: 같은 링크(플랫폼 캠페인 URL은 고유)면 재등록 안 함.
- **최초 제보자**: 수집·자동등록분은 **비움**(특정 개인의 제보가 아니므로). 실제 유저가 앱에서 한 제보는 보존.
- **개인정보(PII)**: 이메일 등은 로그인 유저만, 공개 응답에서 제거.

## 8. 주의 (운영 사고 방지)

- **`.env.local`에 `vercel env pull` 쓰지 말 것** — Vercel의 민감(Sensitive) 변수는 **빈 값으로 내려와** 기존 로컬 키까지 전멸함(2026-08-30 재발). → **보호 훅 도입**: `.claude/hooks/protect-env-local.sh`(PreToolUse, `settings.local.json`에 등록)가 `.env.local`에 대한 Edit/Write·`sed -i`·리다이렉트·`tee`·`cp/mv/rm`·`vercel env pull`을 **자동 차단**(읽기는 허용). 값 수정이 필요하면 훅을 잠시 해제하고 진행. (기존 `.env.local.backup` 안전망은 이 훅으로 대체·삭제)
- **Sensitive 키는 로컬에 못 pull됨** — KAKAO/NAVER OAuth·`ADMIN_PASSWORD`·`SESSION_SECRET` 등은 Vercel 프로덕션에만 있고 복호화 불가. 로컬에 필요하면 각 콘솔에서 직접 복사해 넣어야 함(`SESSION_SECRET`은 로컬 전용 랜덤값도 가능, 단 프로덕션 세션과 비호환).
- **지오코딩/검색 키**(`NAVER_MAPS_KEY_ID`/`NAVER_MAPS_KEY`, `NAVER_SEARCH_*`)는 **로컬 크롤러가 `.env.local`에서 읽음** → 로컬에 반드시 채워야 자동등록이 정확 좌표를 얻음. (수동 autopilot 버튼은 Vercel 서버에서 도니 Vercel 환경변수에도 등록해두면 양쪽 정확)
- **Vercel 키와 로컬 키는 별개 관리** — 한쪽이 죽으면(401) 그쪽 실행은 자동등록 못 하고 검수로만 감. 평소 수집은 로컬 크롤러이므로 `.env.local` 키가 실질적으로 중요.

## 10. DB 읽기 한도·성능 (Turso) — 2026-08-31 사고 후 런북

### 무슨 일이었나
크롤 시작 며칠 만에 **Turso 월 rows-read 한도(Free 500M) 초과 → 계정 전체 차단**(3개 DB 다운). 공개 API(`/api/places`·`/api/campaigns`)가 500이 되어 **앱이 빈 데이터로 뜸**(홈은 200). Free 티어는 Overages가 없어 한도 도달 시 그냥 막고, 리셋은 청구주기 기준(대시보드 표기)이라 대기=한 달 다운.

### 진짜 원인 = 인덱스 없는 전수스캔 (loadDedupe 아님)
크롤러가 매 패스 반복하는 쿼리 중 **인덱스가 없어 전체 테이블을 스캔**하던 것들이 주범(Turso는 스캔한 행을 전부 읽기로 카운트):
- `_autopilot.js` 대기조회 `status='pending' AND COALESCE(auto_seen,0)=0` → `scraped_items` 3.3만 전수스캔 ×패스당 여러 번
- `insertCampaign`의 `WHERE link=?` → `campaigns` 2.7만 전수스캔 ×등록건수
- `insertPlace`의 `REPLACE(name,' ','')` 중복확인 → 인덱스 무력화, 등록마다 places 2만 스캔
- + loadDedupe·autopilot이 매 호출 places/campaigns 전체 재읽기

### 조치 (적용 완료)
- **인덱스 2개 생성**(운영 DB, 재시작 불필요·되돌림 가능): `idx_scraped_status_seen(status,auto_seen)`, `idx_campaigns_link(link)`. + 기존 `idx_places_lat_lng` 재활용.
- **쿼리 수정**: 대기조회 `COALESCE(auto_seen,0)=0`→`auto_seen=0`(NULL 0건 확인); insertPlace 중복확인을 좌표 인덱스 범위조회+앱 이름비교로.
- **패스당 1회 공유**: loadDedupe·autopilot용 places를 크롤러가 패스 시작에 1번 읽어 전 플랫폼/autopilot 호출에 주입.
- **결과: 실측 12.23M→1.26M/10분(~10배↓)**. (상세 결정 [06-decision-log](06-decision-log.md) 2026-08-31)

### 모니터링 (매일)
- `bash scripts/db-usage.sh` — rows read/written 현황 + **전날 대비 증가분** + 80% 경고. (`turso db inspect`는 control-plane이라 읽기 quota 미소모.)
- 활성 크롤러는 **캐치업(active)일 때 읽기 많고, 유휴(idle, auto_seen=0이 0에 근접)면 급감** → 하루 증가분은 유휴 상태에서 재보면 실제 상시비용.

### 읽기가 다시 급증하면 (대응 순서)
1. `scripts/db-usage.sh`로 증가 속도 확인(10분/하루 단위).
2. 크롤러의 새/변경 쿼리 의심 → **`EXPLAIN QUERY PLAN <쿼리>`** 로 `SCAN`(전수) vs `SEARCH USING INDEX` 확인.
3. `SCAN table`이면 그 컬럼에 인덱스 추가(`CREATE INDEX IF NOT EXISTS ...`). **원칙: 크롤러 핫패스(매 패스/매 아이템 실행)의 WHERE 컬럼은 반드시 인덱스.** `REPLACE()`/`COALESCE()`/함수를 WHERE에 쓰면 인덱스가 죽으니 피할 것.
4. 반복 전체읽기는 패스당 1회 로드해 공유.
