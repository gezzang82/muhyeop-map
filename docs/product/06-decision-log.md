# 의사결정 기록

## 2026-08

### 수집 승인/자동등록분은 최초 제보자를 비운다 (2026-08-23)

수동 승인(`approveStaged`)이 매장 생성 시 `source:'admin'`을 안 보내 `places.js`가 **운영자 로그인 세션을 최초 제보자로** 기록하던 버그 수정. 이제 수집 승인·오토파일럿 자동등록분은 매장 최초 제보자가 **비워짐**(수집 데이터는 특정 개인의 제보가 아니므로). 기존 잘못 박힌 43개 매장은 일괄 정정(운영DB), **진짜 유저가 앱에서 먼저 제보한 매장은 보존**(그 매장에 `source='user'` 캠페인이 있으면 제외). 캠페인 제보자는 이전에도 비어 있었음(매장만 누락).

### 수집→검수 워크플로우에 AI 자동등록(오토파일럿) 도입 (2026-08-21)

기존: 스크래핑으로 `scraped_items`(승인 대기)에 쌓고 **운영자가 한 건씩 검수·승인**. 이 수동 승인 자체를 자동화하기로 결정.
- **방향**: 매일 크론이 수집 후 staged를 3갈래로 자동 라우팅 — 🟢 자동등록 / 🟡 사람 검수큐 / 🔴 자동 스킵. **운영자는 🟡만** 본다(전량 검수 → 애매한 것만).
- **처음부터 자동등록 ON, 단 보수적으로**: 조금이라도 애매하면 🟡로. 오등록 0 우선.
- **라우팅 대부분은 결정론적**(`_scrape.js`의 `classify()`+`flags` 재사용). AI 호출은 **신규매장 후보(`new_place`)에만** — 카테고리·내용 정합성 + fuzzy 중복(이름 살짝 다른 기존 매장) 판정. 기존매장 추가(`add_channel`/`renew`)는 좌표OK+flags없으면 규칙만으로 자동등록.
- **AI = OpenAI(GPT)**. 운영자가 보유한 유료 키 사용(`OPENAI_API_KEY`). `fetch` 직접 호출(SDK 의존성 추가 안 함). 소형 모델(gpt-4o-mini급), 하루 수 건이라 비용 사실상 0.
- **서버 지오코딩**: 기존 좌표변환은 브라우저 네이버 지도 JS SDK라 크론(서버·무브라우저)에서 못 씀. 네이버 **로컬 검색 API**(기존 `NAVER_SEARCH` 키 재사용)의 `mapx/mapy`로 서버에서 좌표 획득. 한국 좌표 범위 밖이면 지오코딩 실패로 간주 → 🟡.
- **함수 12개 한도(이미 12/12)**: 새 api 파일 금지 → `campaigns.js`에 `?action=autopilot`으로 합침. 헬퍼는 `_ai.js`/`_geocode.js`(`_` 접두=카운트 제외).
- **안전장치**: ① 자동등록분은 `source='ai'` 태깅 → 어드민에서 "AI 등록분 보기/일괄 회수". ② `?dry=1` 미리보기(라우팅만 하고 실제 등록 안 함). ③ 실행 요약을 `scrape_runs`에 기록. ④ 크론 인증 `CRON_SECRET`.
- 관련: [[project_scraping_plan]], [03-platform-analysis](03-platform-analysis.md).

### 오토파일럿 처리량 = Hobby 하루 1회 시간예산 방식 (2026-08-21)

디너의여왕은 신규가 D-6로 올라오고 **평일 수백 건**. Hobby(크론 1일 1회·함수 300초)에선 상세 1건당 예의상 0.6초라 한 실행 현실 상한 ~150~200건. 셋 중 "**하루 1회 최대치**"(플랜 유지·피크일은 밀리되 주말/한가한 날 자동 소진) 선택.
- **시간예산 파이프라인**: 크론 1회에서 `TOTAL=240s` 안에 ① 오토파일럿 먼저(`AUTOPILOT=150s`, 어제 쌓인 대기 검수·등록 우선 — 수집만 하고 등록 못 하는 상황 방지) ② 남는 시간에 수집(`limit=250` 크게 두고 시간으로 상한). 각 단계 `deadlineTs` 초과 시 중단, 못한 건 **증분커서/`auto_seen`이 다음 실행에서 이어받음**(중단돼도 안전). `vercel.json` `functions.maxDuration=300`.
- 수집 순서를 '수집→오토파일럿'에서 '**오토파일럿→수집**'으로 뒤집음(등록 진척 보장). 그래서 갓 수집분은 다음날 등록(D-6라 여유). 자기균형: 대기 적은 날 수집 많이/많은 날 등록 많이.
- 범위는 서울(jeonche=전체 최신, 증분). 부산·경기·인천/포블로그는 수동 수집해도 오토파일럿이 검수·등록. 더 늘리려면 Pro(하루 여러 번)로.

## 2026-07

### 캠페인 신청 링크(`LINKS_ENABLED`) 켬 — 8/1 예정에서 하루 앞당김 (2026-07-31)

`app.js`의 `LINKS_ENABLED`를 `false`→`true`로 전환. 인포윈도우·상세시트의 캠페인 내용을 클릭하면 해당 플랫폼 상세페이지로 이동(`campaignLink()`). 활성 캠페인 629건 중 626건이 링크 보유. 소프트 오픈 진행에 맞춰 8/1 예정을 하루 앞당겨 켬. (아래 2026-07-27 결정의 실행)

### 앱은 8/1 전 소프트 출시하되, 캠페인 신청 링크(`LINKS_ENABLED`)는 8/1부터 연결 (2026-07-27)

iOS 심사 통과(수동 출시). 앱은 라이브 웹(muhyeop.com)을 그대로 보는 구조라 8/1 전에 조용히 출시(App Store 인덱싱·안정화 버퍼 확보)하고, **정식 오픈 홍보만 8/1**로 분리.
- **단, 각 캠페인의 외부 플랫폼 신청 링크(`c.link`)는 8/1까지 연결하지 않음.** `app.js`의 `LINKS_ENABLED = false`로 링크 버튼 전부 숨김 유지(현 상태). **8/1에 이 한 줄만 `true`로 바꿔 배포**하면 인포윈도우·상세시트의 신청 링크가 노출됨(`campaignLink()`).
- **왜 오픈 전엔 끄나**: Referer로 우리 URL(muhyeop.com)이 파트너 플랫폼에 노출되는 것 방지 + 소프트 출시 기간 외부 플랫폼 대상 노출 최소화(법적/운영 신중).
- 관련: [14-launch-checklist](14-launch-checklist.md) D(오픈 임박 시).

### 쿠폰 이벤트는 오픈 당일 아닌 오픈 +2주(≈8/15)에 진행 (2026-07-25)

제보왕/후기 최다등록자 쿠폰 이벤트를 **오픈(8/1) 당일이 아니라 오픈 2주 뒤(≈8/15)에** 진행하기로.
- **당일 비추 이유**: ① 오픈 당일은 유저가 적어 "1등만 쿠폰"이면 제보 2~3개로도 1등 → 경쟁·유인 약함 ② 소수라 자가제보 어뷰징 쉬움 ③ 쿠폰 노린 저품질 제보가 첫인상 훼손 ④ 이벤트 인프라(제보왕 리더보드 배너=`LEADERBOARD_ENABLED` off, 어드민 집계·당첨자 검증) 미구현.
- **오픈은 "오픈 팝업"(기존 배너 시스템 재활용)으로** 깔끔하게, 이벤트는 유저가 쌓인 2주 뒤. 그 사이 리더보드·집계 화면 구현.
- 오픈 자체는 [14-launch-checklist](14-launch-checklist.md) 참고.

### 최초제보자 후기는 상단 고정 + 뱃지 (2026-07-23)

매장을 최초로 제보(등록)한 사용자(`places.founder_user_id`)가 그 매장에 후기를 쓰면, **정렬(최신/좋아요)과 무관하게 후기 목록 최상단에 고정**하고 **메달 아이콘 + 파란 닉네임 뱃지**를 표시. 발굴자 보상으로 제보→후기 선순환을 강화.
- **품질 신뢰 유지 위해 "신분 뱃지"로 명확화**: 최상단이 "가장 도움되는 후기"가 아니라 "최초 제보자 후기"임을 뱃지로 구분(도움돼요=품질 신호 원칙과 충돌 최소화). Figma 1243-10777.
- 서버(`api/places.js` reviews list)에서 founder_user_id 대조로 `isFounder` 플래그 + ORDER BY 고정. 비로그인 제보 매장(founder_user_id NULL)은 대상 아님.
- 상단 최초제보자 라인 메달 아이콘도 24→20px로 축소(뱃지와 통일).

### 베타 없이 8/1 정식 오픈 (2026-07-23)

기존 계획(7/18 베타 → 8/1 정식)에서 **베타를 건너뛰고 8/1 정식 오픈**으로 변경.
- **제보왕 리더보드 배너**: 계속 숨김 유지(`LEADERBOARD_ENABLED=false`). 데이터가 충분히 쌓인 뒤 재검토.
- **오픈 이벤트 보류**: 베타 기간 전제였던 매장등록 1위 스타벅스 쿠폰 / 후기 최다 등록자 쿠폰 이벤트는 당분간 하지 않음(트래픽 보고 나중에 결정).
- **유령 협찬(마감일 없던 331건) 정리 안 함**: 이미 마감된 것으로 간주. 오픈 후 지도에 오래된 상시 협찬이 계속 뜨면 그때 마감일 잔존 여부만 확인.
- 오픈 전 점검 목록은 [14-launch-checklist](14-launch-checklist.md).

### '내 정보' 기여 통계 3종 = 협찬 제보 / 후기 등록 / 도움돼요 (2026-07-11)

'내 정보'(마이페이지) 카드에 사용자 기여 통계 박스(3칸)를 추가. 세 번째 지표는 **도움돼요(내가 등록한 후기가 받은 좋아요 총합)** 로 확정 — 제보·후기라는 "생산" 지표에 더해 **후기 품질(도움됨) 신호**를 함께 보여주려는 의도([[project_review_feature]]의 도움돼요=품질신호 전략과 연결). Figma node 1316-11314.
- DB 스키마 변경 없음: 3개 모두 기존 테이블 COUNT로 계산(`campaigns.user_id` / `reviews.user_id` / `review_likes`⋈`reviews.user_id`). `api/auth/me.js`가 `reportCount`/`reviewCount`/`helpfulCount`/`visitCount`로 반환.
- 어드민 변경 없음(사용자용 화면). 필요 시 회원목록에 후기수/도움돼요수 노출은 별도 선택사항.

### 종료 매장도 검색으로 선택해 후기를 볼 수 있게 한다. (2026-07-10)

지도 검색에서 캠페인이 종료된 매장명을 검색하면 "현재 진행 중인 협찬이 없는 매장이에요" 알럿만 떴다. 매장은 삭제하지 않고 후기가 남으므로, 종료 매장도 **검색 시 회색핀이 뜨는 줌(17, `GRAY_PIN_MIN_ZOOM`)까지 확대해 핀을 선택하고 상세(후기 탭 기본)를 열도록** 변경(알럿 제거). 활성 매장은 기존대로 줌16 + 캠페인 탭.
(회색핀 = 종료 매장 핀. 저줌에선 클러터 방지로 숨기고 확대 시에만 노출.)
