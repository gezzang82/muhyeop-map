### GNB 포함 전 화면을 '웹'으로 구현(하이브리드 셸 유지) (2026-09-27)
- **질문**: Phase 1 화면(특히 하단 GNB)을 웹으로 vs GNB만 네이티브로?

- **이유**: ① 방문 **74%가 모바일웹**(앱 23%) — 네이티브 GNB는 앱에서만 보여 어차피 웹 GNB를 또 만들어야 함(이중 유지). ② **"웹 배포=앱 즉시 반영"** 최대 강점 유지(네이티브면 탭 추가·수정마다 APK/IPA 재빌드+스토어 심사). ③ iOS 미출시(네이티브 착수 시 iOS 네이티브까지 물림). ④ 단일 코드베이스·일관성.
- **웹이라도 네이티브 체감 확보**: 탭 전환은 풀 리로드 X **클라이언트 뷰 전환**(지도 유지), GNB `position:fixed`+`env(safe-area-inset-bottom)`(홈인디케이터/제스처바), 기존 GPU힌트·`contain` 재활용. iOS 인앱 뷰포트 이력 주의 [[project_ios_inapp_viewport]].
- **네이티브 GNB 재검토 조건**: 앱이 주 채널이 되고 스토어 심사주기를 감수할 때(현재 아님). [[17-travel-pins]]

### 만료 후 후기 등록 = 지도 노출연장(체험중) 폐기, 매장명 아카이브 검색 채택 (2026-09-24)
- **문제**: 타이밍 미스매치. 신청마감→선정→체험(며칠~몇주 뒤)→블로그 후기→무협맵 등록. 우리는 신청마감에 캠페인을 자동 미노출하는데, 후기는 한참 뒤라 등록하려면 캠페인이 사라져 있음.
- **검토했다 폐기한 안(체험중 노출 연장)**: 마감 캠페인을 '체험중' 태그로 지도에 더 노출. **폐기 이유** ① 무협맵은 신청 플랫폼이 아니라 **발견 레이어** → 누가 선정됐는지·체험기간이 언제인지 데이터가 없어 '체험중'은 신청마감+N일 **추측**(부정확) ② 블로그 후기는 몇 주~몇 달 뒤에도 와 체험중까지 연장해도 **늦은 후기는 여전히 등록 불가**(핵심 미해결) ③ 신청 불가 캠페인 재노출 = 방금 고친 '협찬종료' 문제 재발.
- **결정**: 노출 연장 대신 **후기 등록을 매장명 아카이브 검색으로** 처리. 무협맵은 **매장 중심**이라 후기는 캠페인이 아니라 **매장에 연결**. 유저는 자기 블로그에 남은 매장명을 그대로 무협맵에서 검색(A안). 캠페인 카드로 인지시키는 B안은 불필요한 결합이라 기각(블로그가 곧 매장명 원장).
- **플로우**: 후기 남기기 → 매장명 검색(전체 매장, 캠페인 만료·유무 무관) → 있으면 선택→블로그 링크로 후기 등록 / 없으면 이름으로 매장 직접 생성→후기.
- **대부분 구현돼 있음**: `searchPlacesOnServer`가 `/api/places?q=이름`으로 전체 비숨김(죽은 매장 포함) 검색→`focusPlace`로 죽은 매장도 후기 등록 가능하게 이미 설계됨([[frontend]] 지도 경량화 v2). 커뮤니티 탭에 **진입점/UX만** 추가하면 됨.
- **보완 넛지**: '체험중' 직감의 좋은 버전 = 지도 연장이 아니라 **커뮤니티에 "최근 마감 협찬 — 다녀오셨다면 후기 남겨주세요" 리스트**('최근 마감'은 정확히 아는 값, 후기 요청·공생 넛지).
- **맥락**: 하단 GNB(홈/즐겨찾기/커뮤니티/마이페이지/메뉴) + 여행지 핀(리텐션) 논의 중 파생. 커뮤니티=후기, 제보하기 탭은 제거 방향. GNB·핀 세부는 스코핑 진행 중([[10-growth-strategy]]).

- **카테고리 규칙**: **음식점>뷰티>카페** 가중 랜덤(`CAT_WEIGHT={음식점:5,뷰티:3,카페:2}`, 후보 있는 것만) → 그 안 1건 랜덤. **이 3개만 대상**, 셋 다 없으면 스킵. 음식점이 신규의 ~75%라 자연히 비중 최고 + 가끔 뷰티/카페로 변화(단조로움 방지). 실시간 GPS 아님 = 저장된 관심지역(집) 기준(바로 체험 못 가니 실시간 무의미).

- **확인**: 온디바이스에서 종료→탭→매장 바텀시트, 포그라운드 자동이동 모두 확인.

### 지도 경량화 v2 — "활성 OR 후기 매장만 노출" + 검색은 서버 전체 (2026-09-10 계획 → ✅ 2026-09-11 구현·배포)

**구현 완료(2026-09-11)**: `GET /api/places?map=1`(활성 캠페인 OR 후기 매장만·hasReview 플래그) + `?q=이름`(전체 비숨김 매장 서버검색). 클라 `loadInitialData`가 `?map=1` 사용(39,154→20,770, 8.2MB→4.9MB). 죽은 매장 지도 제외, 후기 매장은 dim 없이 정상 노출(회색핀). `searchRegion`은 in-memory(map-set) 미스 시 `searchPlacesOnServer`가 `?q=`로 전체 검색→결과 병합→focus(죽은 매장도 검색→후기 등록 가능). 검증: 20,770건 4.9MB·죽은매장 검색 서버폴백 정상. 아래는 원 계획.


경쟁사(blogreviewzip·moaview) 지도 벤치마킹 결과: **같은 네이버 엔진, 마커당 크기도 비슷(우리 219 vs 그들 245 bytes)**. 차이는 **마커 수** — blogreviewzip은 활성 캠페인 11.8k(2.9MB)만, 우리는 **매장 전량 39,154(8.2MB, 죽은 매장 15,942 포함)** 를 다 올려 초기 파싱이 무거움. 개선 방향 확정:
- **지도 표시 대상 = 활성 캠페인 OR 후기 있는 매장(현재 23,212, 59%)** → 죽은 매장 15,942 제외. 로드 8.2MB→~4.9MB, 파싱 4만→2.3만 객체.
- **핀 3-상태**: ①활성=카테고리 컬러핀 ②활성 없지만 **후기 있음=dim 안 함, 정상 노출**(후기 가치) + 후기 표시 ③활성·후기 둘 다 없음=**지도 제외**. → 기존 회색 dim 핀(opacity 0.5, no-active)은 사실상 소멸(죽은 매장이 빠지므로).
- **검색은 서버 전체 대상**: 죽은 매장도 **검색→선택→후기 등록**이 가능해야 하므로(후기 기능 유지가 이유), `searchRegion`을 in-memory(23k)가 아닌 **서버 `/api/places?q=`(전체 39k, 숨김 제외)** 로. 지역검색·후기용 매장검색 공용.
- **구현**: ①`/api/places?map=1`(활성 OR 후기, 마커용 최소필드) ②`/api/places?q=`(서버 검색) ③클라 `loadInitialData`→`?map=1`, `searchRegion`→서버, 검색으로 찾은 지도밖 매장은 focus 시 임시마커로 표시(후기 진입) ④후기 등록 store search를 서버검색으로. **여러 흐름(지도·검색·후기) 동시 변경이라 집중 세션에서 테스트하며 진행**(반쪽 배포 시 지도/검색 깨짐 위험). 이전 "매장 bbox화 후속 Phase"([[frontend]] 캠페인 뷰포트 로딩)의 실제 착수안.

### 초반 로딩(첫 핀 노출) 단축 (2026-09-03)

원우씨 지적: 앱 켜면 핀 뜰 때까지 시간이 걸려 "협찬 없는 지도"로 오해하고 이탈할 수 있음. 부팅 시퀀스 분석 결과 3가지 병목:
1. **로그인 인증(`/api/auth/me`)이 지도 표시를 `await`로 막음** — 핀에 인증 불필요한데 앞을 막음.
2. **캠페인은 지도가 뜬 뒤 idle에서야 로드 시작** → 첫 핀이 그만큼 늦음.
3. **로딩 애니메이션이 핀 그려지기 전에 사라짐** → 빈 지도 오해.

**조치**(app.js):

### 오토파일럿 검수 과잉(오탐) 축소 — 자율화 강화 (2026-08-27)

수동 검수 비중이 과함(월~목 자동 35 vs 수동 187). 원인은 **중복 오탐**: AI에 넘기는 유사매장 목록을 이름 bigram만으로 뽑아, 프랜차이즈 다른 지점("헤비스테이크 과천중앙점"↔"안산중앙점")·이름 일부만 겹치는 다른 업체("홍봉선간장게장"↔"봉선화빛")까지 "중복의심"으로 전부 검수행. 세 가지 수정으로 사람 손 최소화:
1. **위치 기반 중복 판정**: 유사매장 후보를 **반경 300m 이내**로 한정(`similarNearby`, `_autopilot.js`). 먼 동명·유사명은 다른 매장으로 간주 → 오탐 제거. AI 프롬프트도 "같은 브랜드 다른 지점·부분겹침은 중복 아님, 애매하면 null" 명시(`_ai.js`).
2. **요일 불확실 → 검수 안 보내고 요일 비워 등록**(공개화면 요일 미노출). 요일 관련 플래그(`가능요일확인`/`요일·공휴일 재확인`)는 자동등록 차단 안 함.
3. **카테고리 불확실도 비차단**: 신규매장은 AI가 카테고리 판단, 기존매장은 기존 값 유지. 남는 차단성 경고는 채널 없음(등록 불가)뿐.
→ 검수큐는 "채널없음·좌표실패·AI 저신뢰·같은 위치 진짜 중복"만. [[project_scraping_plan]], `13-ai-automation`.

### 크론 순서를 '수집 → 오토파일럿'으로 되돌림 (2026-08-24)

2026-08-21에 '오토파일럿 먼저 → 수집'으로 뒀는데, 실제로는 **역효과**. 대기열이 자주 비어(주말·운영자가 수동으로 다 처리) 오토파일럿이 빈 큐에서 0건 등록 후, 그 뒤 수집된 오늘 신규는 **다음날에야** 오토파일럿 차례가 옴 → 그 전에 운영자가 수동 승인해버려 **자동등록이 사실상 0**(2026-08-24 월 첫 평일: autopilot 0건, 수집 111건, 운영자 수동 110건). 순서를 **수집 먼저 → 그 신규까지 같은 실행에서 오토파일럿**으로 변경. 수집에 상한 `SCRAPE_MS=100s`를 둬 오토파일럿이 항상 돌 시간(~140s) 확보(원래 '오토파일럿 먼저'의 목적이던 "수집이 시간 다 먹는 것" 방지를 상한으로 대체). 하루에 다 못 하면 나머지는 다음 실행/수동(증분·auto_seen 안전).

### 수집 승인/자동등록분은 최초 제보자를 비운다 (2026-08-23)

수동 승인(`approveStaged`)이 매장 생성 시 `source:'admin'`을 안 보내 `places.js`가 **운영자 로그인 세션을 최초 제보자로** 기록하던 버그 수정. 이제 수집 승인·오토파일럿 자동등록분은 매장 최초 제보자가 **비워짐**(수집 데이터는 특정 개인의 제보가 아니므로). 기존 잘못 박힌 43개 매장은 일괄 정정(운영DB), **진짜 유저가 앱에서 먼저 제보한 매장은 보존**(그 매장에 `source='user'` 캠페인이 있으면 제외). 캠페인 제보자는 이전에도 비어 있었음(매장만 누락).

### 수집→검수 워크플로우에 AI 자동등록(오토파일럿) 도입 (2026-08-21)

기존: 스크래핑으로 `scraped_items`(승인 대기)에 쌓고 **운영자가 한 건씩 검수·승인**. 이 수동 승인 자체를 자동화하기로 결정.
- **방향**: 매일 크론이 수집 후 staged를 3갈래로 자동 라우팅 — 🟢 자동등록 / 🟡 사람 검수큐 / 🔴 자동 스킵. **운영자는 🟡만** 본다(전량 검수 → 애매한 것만).
- **처음부터 자동등록 ON, 단 보수적으로**: 조금이라도 애매하면 🟡로. 오등록 0 우선.
- **라우팅 대부분은 결정론적**(`_scrape.js`의 `classify()`+`flags` 재사용). AI 호출은 **신규매장 후보(`new_place`)에만** — 카테고리·내용 정합성 + fuzzy 중복(이름 살짝 다른 기존 매장) 판정. 기존매장 추가(`add_channel`/`renew`)는 좌표OK+flags없으면 규칙만으로 자동등록.
- **AI = OpenAI(GPT)**. 운영자가 보유한 유료 키 사용(`OPENAI_API_KEY`). `fetch` 직접 호출(SDK 의존성 추가 안 함). 소형 모델(gpt-4o-mini급), 하루 수 건이라 비용 사실상 0.
- **서버 지오코딩**: 기존 좌표변환은 브라우저 네이버 지도 JS SDK라 크론(서버·무브라우저)에서 못 씀. 네이버 **로컬 검색 API**(기존 `NAVER_SEARCH` 키 재사용)의 `mapx/mapy`로 서버에서 좌표 획득. 한국 좌표 범위 밖이면 지오코딩 실패로 간주 → 🟡.
- **함수 12개 한도(이미 12/12)**: 새 api 파일 금지 → `campaigns.js`에 `?action=autopilot`으로 합침. 헬퍼는 `_ai.js`/`_geocode.js`(`_` 접두=카운트 제외).
- **안전장치**: ① 자동등록분은 `source='ai'` 태깅 → 어드민에서 "AI 등록분 보기/일괄 회수". ② `?dry=1` 미리보기(라우팅만 하고 실제 등록 안 함). ③ 실행 요약을 `scrape_runs`에 기록. ④ 크론 인증 `CRON_SECRET`.
- 관련: [[project_scraping_plan]], [03-platform-analysis](03-platform-analysis.md).

### 오토파일럿 처리량 = Hobby 하루 1회 시간예산 방식 (2026-08-21)

디너의여왕은 신규가 D-6로 올라오고 **평일 수백 건**. Hobby(크론 1일 1회·함수 300초)에선 상세 1건당 예의상 0.6초라 한 실행 현실 상한 ~150~200건. 셋 중 "**하루 1회 최대치**"(플랜 유지·피크일은 밀리되 주말/한가한 날 자동 소진) 선택.
- **시간예산 파이프라인**: 크론 1회에서 `TOTAL=240s` 안에 ① 오토파일럿 먼저(`AUTOPILOT=150s`, 어제 쌓인 대기 검수·등록 우선 — 수집만 하고 등록 못 하는 상황 방지) ② 남는 시간에 수집(`limit=250` 크게 두고 시간으로 상한). 각 단계 `deadlineTs` 초과 시 중단, 못한 건 **증분커서/`auto_seen`이 다음 실행에서 이어받음**(중단돼도 안전). `vercel.json` `functions.maxDuration=300`.
- 수집 순서를 '수집→오토파일럿'에서 '**오토파일럿→수집**'으로 뒤집음(등록 진척 보장). 그래서 갓 수집분은 다음날 등록(D-6라 여유). 자기균형: 대기 적은 날 수집 많이/많은 날 등록 많이.
- 범위는 서울(jeonche=전체 최신, 증분). 부산·경기·인천/포블로그는 수동 수집해도 오토파일럿이 검수·등록. 더 늘리려면 Pro(하루 여러 번)로.
