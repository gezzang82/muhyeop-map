### Turso 읽기한도 초과(앱 데이터 다운) → 크롤러 중복확인 읽기 대폭 절감 (2026-08-31)

월 읽기 한도 초과로 Turso가 **읽기 차단** → 공개 API(`/api/places`, `/api/campaigns?active=1`)가 500, 앱이 빈 데이터로 뜸(홈 200). **원인 규명**:
- (오해정정) 엣지 캐싱은 **정상 작동 중**이었음. 응답의 `cache-control: public, max-age=0, must-revalidate`는 Vercel이 s-maxage를 CDN 캐시로만 쓰고 브라우저엔 캐시 안 시킬 때 보내는 정상 헤더. 방문자 경로는 문제 아님.
- **진짜 주범: 크롤러 `loadDedupe`(전체 매장+전체 캠페인 ≈3.8만 행 통읽기)를 한 바퀴에 ~39회 호출** — 디너의여왕 서울 17개 하위지역마다 1회, 리뷰노트 17개 시/도마다 1회, 나머지 5개 플랫폼 각 1회. 바퀴당 ~150만 행, 하루종일 돌면 수천만~수억 행. + 당일 대규모 전수감사(전체 반복조회)가 얹힘.
- **해결(코드)**: 디너의여왕 하위지역 루프·리뷰노트 시/도 루프는 **autopilot(등록)이 루프가 끝난 뒤 1회만 돌므로**, 루프 전에 `loadDedupe`를 **1번만 읽어 공유**해도 신선도 손실 0. `runScrape`/`runDinnerqueen`/`runReviewnote`에 optional `dedupe` 인자 추가, `crawl-worker.js`가 지역 루프 전에 1회 로드해 주입. **바퀴당 loadDedupe ~39→~7회**. 쓰기 시점의 이름+좌표 중복매장 가드가 남아 있어 정확성도 안전. 추가로 유휴 대기 10분→30분(유휴 패스 읽기 절감, daily 갱신이라 무해).
- **진짜 주범 재규명 + 인덱스(측정 기반)**: loadDedupe 수정 후에도 실측 10분 읽기가 오히려 늘어(9.48M→12.23M) 재분석 → **인덱스 없는 전체 스캔이 본체**였음. ①`_autopilot.js`가 대기건을 `status='pending' AND COALESCE(auto_seen,0)=0`로 매 호출 `scraped_items` 3.3만 전수스캔(패스당 9회) ②`insertCampaign`의 `WHERE link=?`가 인덱스 없어 캠페인 등록/확인마다 `campaigns` 2.7만 전수스캔 ③`insertPlace`의 `REPLACE(name,' ','')` 중복확인이 인덱스 무력화로 등록마다 places 2만 스캔 ④autopilot이 호출마다 places 전체 재읽기. **조치**: `CREATE INDEX idx_scraped_status_seen(status,auto_seen)`(auto_seen NULL 0건 확인 후 `COALESCE` 제거)·`CREATE INDEX idx_campaigns_link(link)`; insertPlace 중복확인을 좌표 인덱스(`idx_places_lat_lng`) 범위조회+앱 이름비교로; loadDedupe·autopilot용 places를 **패스당 1회** 로드해 전 플랫폼/autopilot 호출이 공유(runXxx·runScrape·runAutopilot에 optional `dedupe`/`places` 주입). **실측: 12.23M→1.26M/10분(~10배↓)**. 인덱스는 즉시 적용(재시작 불필요). **교훈: "왜 읽기가 많나"는 대개 인덱스 없는 전수스캔 — EXPLAIN QUERY PLAN으로 확인.**
- **일일 사용량 모니터**: `turso db inspect`(control-plane, 읽기 quota 미소모)로 rows read/written 확인. `scripts/db-usage.sh`가 전날 대비 증가분·80% 경고 출력. (Turso CLI `db usage`는 이 버전에 없어 `inspect` 사용)
- **즉시 복구**: Free 티어는 Overages 없이 한도 도달 시 **계정 전체 차단**(3개 DB 다운), 리셋은 청구주기 기준(대시보드 표기 10/1)이라 대기=한 달 다운. → **Developer($5.99/월)로 업그레이드**해 즉시 해제(원우씨 결제 완료, 앱 복구 확인).
- **데이터 로드 실패 폴백 화면 추가**: 기존엔 API 500 시 `placesRes.json()`이 텍스트 응답에서 터져 **로딩 스피너 무한**이었음. `loadInitialData`가 `!res.ok`·비배열을 감지해 던지고 부팅 핸들러가 잡아 기존 `#mapError` 오버레이("지도를 불러오지 못했어요 / 다시 시도")를 재사용. 실패 시 `_dataLoadPromise` 메모 해제로 재시도 가능. `.map-error`를 `position:fixed;z-index:10000`로, `showMapError`가 오버레이를 `body` 최상위로 이동(부모 스태킹 컨텍스트 탈출) → **PC 사이드바·아이콘레일·라이브캐릭터까지 화면 전체를 덮음**. 실제 500 상태로 검증 완료.

### AI 판정 기준 완화 — 기본 승인, 명확한 문제만 반려 (2026-08-27)

키 복구 후에도 검수가 과함. AI가 정상 체험단 협찬을 "내용 불명확/광고성"이라며 confidence 0.5~0.8로 반려(메트로삼겹살·인생락국수 등 멀쩡한 가게). 체험단 협찬 내용은 원래 짧고 홍보성이라 그게 정상인데 AI 기준이 과함. `_ai.js` 프롬프트를 **기본 approve=true, 명확한 문제(스팸 매장명·배송형·같은위치 중복)만 반려**로 재작성 + **신뢰도 임계값 0.85→0.6**. 1차 필터(서울·주소·비배송형)를 이미 통과한 플랫폼 정상 데이터라는 전제 명시. 실측: 반려됐던 8건 재판정 시 전부 0.90 승인.

### 크롤 처리량 최대화(무료) + 로컬 크롤 워커 도입 (2026-08-27)

디너의여왕 신규가 하루 ~300건인데 Vercel 크론은 하루 1회·300초라 ~45건만 처리(수집 상한 100초 탓). 무료 범위에서 최대화:
- **Vercel 크론 튜닝**: 상세 fetch 딜레이 600→300ms, 수집 예산 `SCRAPE_MS` 100→190초, 전체 `TOTAL_MS` 240→280초(300초 한계 버퍼 20초). → 하루 ~90~120건.
- **로컬 크롤 워커**(`scripts/crawl-worker.js`): 컴퓨터 켜져 있을 때 서버 코드(`_scrape`/`_autopilot`)를 그대로 재사용해 운영 Turso DB에 직접 수집+자동등록을 **무제한 반복**. Vercel 300초·1일1회 제약 우회. 커서/`auto_seen` 기반이라 크론과 겹쳐도 안전(UNIQUE로 중복 무시). `.env.local`에 `OPENAI_API_KEY` 추가 시 신규매장도 로컬 자동등록(없으면 검수큐).
- 근본 한계: 상세 fetch가 건당 ~2초라 Vercel 1회로는 ~150건이 천장. 전량(300+)/실시간은 로컬 워커 또는 Vercel Pro(하루 여러 번)로. 병렬 fetch는 커서 로직·정책(저빈도) 때문에 보류.

### 오토파일럿 검수 과잉(오탐) 축소 — 자율화 강화 (2026-08-27)

수동 검수 비중이 과함(월~목 자동 35 vs 수동 187). 원인은 **중복 오탐**: AI에 넘기는 유사매장 목록을 이름 bigram만으로 뽑아, 프랜차이즈 다른 지점("헤비스테이크 과천중앙점"↔"안산중앙점")·이름 일부만 겹치는 다른 업체("홍봉선간장게장"↔"봉선화빛")까지 "중복의심"으로 전부 검수행. 세 가지 수정으로 사람 손 최소화:
1. **위치 기반 중복 판정**: 유사매장 후보를 **반경 300m 이내**로 한정(`similarNearby`, `_autopilot.js`). 먼 동명·유사명은 다른 매장으로 간주 → 오탐 제거. AI 프롬프트도 "같은 브랜드 다른 지점·부분겹침은 중복 아님, 애매하면 null" 명시(`_ai.js`).
2. **요일 불확실 → 검수 안 보내고 요일 비워 등록**(공개화면 요일 미노출). 요일 관련 플래그(`가능요일확인`/`요일·공휴일 재확인`)는 자동등록 차단 안 함.
3. **카테고리 불확실도 비차단**: 신규매장은 AI가 카테고리 판단, 기존매장은 기존 값 유지. 남는 차단성 경고는 채널 없음(등록 불가)뿐.
→ 검수큐는 "채널없음·좌표실패·AI 저신뢰·같은 위치 진짜 중복"만. [[project_scraping_plan]], `13-ai-automation`.

### 크론 순서를 '수집 → 오토파일럿'으로 되돌림 (2026-08-24)

2026-08-21에 '오토파일럿 먼저 → 수집'으로 뒀는데, 실제로는 **역효과**. 대기열이 자주 비어(주말·운영자가 수동으로 다 처리) 오토파일럿이 빈 큐에서 0건 등록 후, 그 뒤 수집된 오늘 신규는 **다음날에야** 오토파일럿 차례가 옴 → 그 전에 운영자가 수동 승인해버려 **자동등록이 사실상 0**(2026-08-24 월 첫 평일: autopilot 0건, 수집 111건, 운영자 수동 110건). 순서를 **수집 먼저 → 그 신규까지 같은 실행에서 오토파일럿**으로 변경. 수집에 상한 `SCRAPE_MS=100s`를 둬 오토파일럿이 항상 돌 시간(~140s) 확보(원래 '오토파일럿 먼저'의 목적이던 "수집이 시간 다 먹는 것" 방지를 상한으로 대체). 하루에 다 못 하면 나머지는 다음 실행/수동(증분·auto_seen 안전).

### 수집 승인/자동등록분은 최초 제보자를 비운다 (2026-08-23)

수동 승인(`approveStaged`)이 매장 생성 시 `source:'admin'`을 안 보내 `places.js`가 **운영자 로그인 세션을 최초 제보자로** 기록하던 버그 수정. 이제 수집 승인·오토파일럿 자동등록분은 매장 최초 제보자가 **비워짐**(수집 데이터는 특정 개인의 제보가 아니므로). 기존 잘못 박힌 43개 매장은 일괄 정정(운영DB), **진짜 유저가 앱에서 먼저 제보한 매장은 보존**(그 매장에 `source='user'` 캠페인이 있으면 제외). 캠페인 제보자는 이전에도 비어 있었음(매장만 누락).

### 수집→검수 워크플로우에 AI 자동등록(오토파일럿) 도입 (2026-08-21)

기존: 스크래핑으로 `scraped_items`(승인 대기)에 쌓고 **운영자가 한 건씩 검수·승인**. 이 수동 승인 자체를 자동화하기로 결정.
- **방향**: 매일 크론이 수집 후 staged를 3갈래로 자동 라우팅 — 🟢 자동등록 / 🟡 사람 검수큐 / 🔴 자동 스킵. **운영자는 🟡만** 본다(전량 검수 → 애매한 것만).
- **처음부터 자동등록 ON, 단 보수적으로**: 조금이라도 애매하면 🟡로. 오등록 0 우선.
- **라우팅 대부분은 결정론적**(`_scrape.js`의 `classify()`+`flags` 재사용). AI 호출은 **신규매장 후보(`new_place`)에만** — 카테고리·내용 정합성 + fuzzy 중복(이름 살짝 다른 기존 매장) 판정. 기존매장 추가(`add_channel`/`renew`)는 좌표OK+flags없으면 규칙만으로 자동등록.
- **AI = OpenAI(GPT)**. 운영자가 보유한 유료 키 사용(`OPENAI_API_KEY`). `fetch` 직접 호출(SDK 의존성 추가 안 함). 소형 모델(gpt-4o-mini급), 하루 수 건이라 비용 사실상 0.
- **서버 지오코딩**: 기존 좌표변환은 브라우저 네이버 지도 JS SDK라 크론(서버·무브라우저)에서 못 씀. 네이버 **로컬 검색 API**(기존 `NAVER_SEARCH` 키 재사용)의 `mapx/mapy`로 서버에서 좌표 획득. 한국 좌표 범위 밖이면 지오코딩 실패로 간주 → 🟡.
- **함수 12개 한도(이미 12/12)**: 새 api 파일 금지 → `campaigns.js`에 `?action=autopilot`으로 합침. 헬퍼는 `_ai.js`/`_geocode.js`(`_` 접두=카운트 제외).
- **안전장치**: ① 자동등록분은 `source='ai'` 태깅 → 어드민에서 "AI 등록분 보기/일괄 회수". ② `?dry=1` 미리보기(라우팅만 하고 실제 등록 안 함). ③ 실행 요약을 `scrape_runs`에 기록. ④ 크론 인증 `CRON_SECRET`.
- 관련: [[project_scraping_plan]], [03-platform-analysis](03-platform-analysis.md).

### 오토파일럿 처리량 = Hobby 하루 1회 시간예산 방식 (2026-08-21)

디너의여왕은 신규가 D-6로 올라오고 **평일 수백 건**. Hobby(크론 1일 1회·함수 300초)에선 상세 1건당 예의상 0.6초라 한 실행 현실 상한 ~150~200건. 셋 중 "**하루 1회 최대치**"(플랜 유지·피크일은 밀리되 주말/한가한 날 자동 소진) 선택.
- **시간예산 파이프라인**: 크론 1회에서 `TOTAL=240s` 안에 ① 오토파일럿 먼저(`AUTOPILOT=150s`, 어제 쌓인 대기 검수·등록 우선 — 수집만 하고 등록 못 하는 상황 방지) ② 남는 시간에 수집(`limit=250` 크게 두고 시간으로 상한). 각 단계 `deadlineTs` 초과 시 중단, 못한 건 **증분커서/`auto_seen`이 다음 실행에서 이어받음**(중단돼도 안전). `vercel.json` `functions.maxDuration=300`.
- 수집 순서를 '수집→오토파일럿'에서 '**오토파일럿→수집**'으로 뒤집음(등록 진척 보장). 그래서 갓 수집분은 다음날 등록(D-6라 여유). 자기균형: 대기 적은 날 수집 많이/많은 날 등록 많이.
- 범위는 서울(jeonche=전체 최신, 증분). 부산·경기·인천/포블로그는 수동 수집해도 오토파일럿이 검수·등록. 더 늘리려면 Pro(하루 여러 번)로.

- DB 스키마 변경 없음: 3개 모두 기존 테이블 COUNT로 계산(`campaigns.user_id` / `reviews.user_id` / `review_likes`⋈`reviews.user_id`). `api/auth/me.js`가 `reportCount`/`reviewCount`/`helpfulCount`/`visitCount`로 반환.
- 어드민 변경 없음(사용자용 화면). 필요 시 회원목록에 후기수/도움돼요수 노출은 별도 선택사항.

### 종료 매장도 검색으로 선택해 후기를 볼 수 있게 한다. (2026-07-10)

지도 검색에서 캠페인이 종료된 매장명을 검색하면 "현재 진행 중인 협찬이 없는 매장이에요" 알럿만 떴다. 매장은 삭제하지 않고 후기가 남으므로, 종료 매장도 **검색 시 회색핀이 뜨는 줌(17, `GRAY_PIN_MIN_ZOOM`)까지 확대해 핀을 선택하고 상세(후기 탭 기본)를 열도록** 변경(알럿 제거). 활성 매장은 기존대로 줌16 + 캠페인 탭.
(회색핀 = 종료 매장 핀. 저줌에선 클러터 방지로 숨기고 확대 시에만 노출.)

### 매장은 삭제하지 않는다.

캠페인이 종료되어도 매장은 유지한다.

### 후기는 네이버 블로그만 지원한다.

블로그 유입과 정보량을 고려한 결정.
